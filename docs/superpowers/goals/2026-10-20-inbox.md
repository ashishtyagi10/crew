# Goal — a light Gmail inbox in a pane: `/inbox`

**Status: SET 2026-10-20** (the user: "go ahead with the inbox goal"). Phase 0 researched and
built; phase 1 shipped in v0.27.29, sign-in not yet tried against Google live (see "Where it
stands" at the end).

**Set:** 2026-10-20 by the user: *"Write a goal to add support for gmail client within crew,
that can be accessed via `/inbox` command and should be light weight."*

## Why it fits, and where it could go wrong

crew is already more than a shell host. `/todo`, `/weather` and `/far` over Google Drive are all
in it, and the JARVIS goal (2026-08-23) wants a resident assistant. Mail fits that if it does
what a terminal does well: glance, triage by keyboard, and hand a thread to agent smith. It does
not fit if it grows into a mail client. Smith can already reach Gmail through an MCP server
(`tier_of("gmail", "send")` already needs approval in `crates/crew-plugin/src/broker/tier.rs`).
What a native pane adds is the glance and the keys, not access.

The risks, most serious first:
1. **Google sign-in.** Every Gmail scope that reads mail (`gmail.readonly`, `gmail.modify`) is a
   *restricted* scope. A public app that asks for one needs Google's verification and a security
   assessment, so crew cannot ship a client ID of its own. Each user creates a Desktop OAuth
   client in their own Google Cloud project. Bring-your-own key is the model crew already uses
   for providers. While that client is in "Testing", its refresh tokens expire after 7 days. In
   "Production" but unverified, the user clicks through an "unverified app" screen once. Both
   claims need checking against Google's current docs in phase 0.
2. **Prompt injection.** Mail is text written by strangers. Anything smith reads from the inbox
   is data, fenced and labelled untrusted. Smith never sends mail.
3. **Scope creep.** Each phase below has a "not in this goal" line, and the line holds.

## What "light weight" means here (measurable)

- **No new dependency.** Gmail's REST API is JSON over HTTPS: `reqwest`, `serde_json` and
  `base64` (for base64url bodies) are already in the workspace. There is no IMAP and no MIME
  crate. HTML mail becomes text through the reader that `sys:fetch` already uses
  (`crates/crew-plugin/src/broker/sysfetchtext.rs`).
- **No mail store on disk.** Only the refresh token is saved, in `credentials.json` beside the
  provider keys (`crates/crew-plugin/src/credentials.rs`). The current page of threads lives in
  memory and is gone when the pane closes.
- **Few calls.** The unread count is one call (`labels/INBOX` returns `threadsUnread`). The list
  is `threads.list` plus `format=metadata` for From, Subject and Date. Later refreshes go
  through `history.list` from the last `historyId`, which costs one small call when nothing
  changed. The pane polls every 60 s while it is visible and every 5 min for the glance card,
  and makes no calls at all when neither is showing.
- **Small code.** About 1,500 lines in total, every file under the 200-line cap, with tests
  against a local stub server (the pattern in `crates/crew-plugin/tests/common/oauthstub.rs`).

## Done means

**Phase 0 — prove the sign-in (a spike, no pane yet).**
1. A Desktop OAuth client, signed in through a loopback redirect with PKCE. Reuse the callback
   parser and listener from OpenRouter's browser sign-in (`crates/crew-app/src/oauth.rs`).
2. Write down from Google's docs, with links: the scopes, the token lifetime in Testing and in
   Production, and the steps a user takes to make a client. If they take more than about
   5 minutes, or the token dies weekly with no way out, stop and bring it back to the user
   before phase 1.

**Phase 1 — a read-only inbox (`gmail.readonly`).**
3. `/inbox` opens or focuses an inbox pane: a rounded card with a fieldset legend
   (`inbox · 12 unread`), auto-tiled like every pane. Not signed in, the pane is the sign-in:
   paste the client ID once, the browser opens, done. This is the pattern `/model <provider>`
   uses to sign in (`crates/crew-app/src/modelsignin.rs`).
4. Each row shows an unread dot, the sender (bold when unread), the subject, a muted snippet,
   and the age right-aligned. Rows fold to fit at every pane width.
5. Keys: `↑↓` move, `Enter` reads the thread in the pane (plain text; HTML read as text), `Esc`
   goes back to the list, `/` searches with Gmail's own syntax (`from:`, `is:unread`), `r`
   refreshes, `o` opens the thread in the browser. `/inbox <query>` opens on a search.
6. An INBOX glance card in the nav (unread count) works like WEATHER
   (`crates/crew-app/src/navweathercard.rs`). It shows only when signed in, and it is the
   first card dropped when the nav is short.
7. Shown in light, dark and a glass theme. A test proves the token never reaches a log, a panic
   message or `{:?}`. README and `docs/CREW.md` list `/inbox` and any `CREW_*` knob. Control
   characters in mail are stripped before they reach the grid.

**Phase 2 — triage (`gmail.modify`).**
8. `e` archives, `u` undoes, `m` marks read or unread, `s` stars. Each takes one key and shows
   one line of feedback. Nothing is ever deleted.

**Phase 3 — agent smith on the inbox.**
9. `a` hands the open thread to smith as fenced, untrusted data: "summarise", "what do they
   want from me".
10. `t` turns a thread into a `/todo` row, with the subject, a link back, and a due date taken
    from the thread ("by Friday").
11. Smith may write a reply as a **draft** (`gmail.compose`). The draft waits in Gmail, and the
    user sends it there. No send key exists in crew.

## Not in this goal

Sending mail, downloading attachments (names and sizes only; `o` opens the web), rendering HTML,
more than one account, an offline store, notifications beyond the glance card, IMAP, and other
providers (Outlook, Fastmail). Each would be a goal of its own, set only if this one is used.

## Where it stands (2026-10-20)

**Phase 0, from Google's docs** (read 2026-10-20; full notes with links kept by the session):
- Desktop flow: loopback `http://127.0.0.1:<random port>` (no port is registered for a Desktop
  client), PKCE S256, `state`, auth `https://accounts.google.com/o/oauth2/v2/auth`, token
  `https://oauth2.googleapis.com/token`. The copy-paste (OOB) flow is gone since 2023.
  [native-app guide](https://developers.google.com/identity/protocols/oauth2/native-app)
- Every Gmail scope that reads mail is **restricted**, `gmail.metadata` included (and it blocks
  search), so the client is the user's own and `gmail.readonly` is asked for from the start.
  [scopes](https://developers.google.com/workspace/gmail/api/auth/scopes)
- An app in **Testing** has its sign-in ended after 7 days; **In production** but unverified,
  a personal app under 100 users clicks through one "unverified app" screen and has no weekly
  expiry. The setup page says to Publish. [Testing expiry](https://developers.google.com/identity/protocols/oauth2#expiration)
- Quota changed 2026-05-01: 6,000 units per user per minute for new projects; a 25-thread page
  is about 1,000. The pane lists once and then polls the profile's `historyId` (1 unit).
  [quota](https://developers.google.com/workspace/gmail/api/reference/quota)
- Setup is 4–6 minutes for someone who knows the Cloud console, 8–12 the first time (estimate).
  Two things keep it short: the page opens the five console pages in order, and crew finds the
  downloaded `client_secret_*.json` itself.

**Shipped in v0.27.29 (phases 0–1):** `/inbox`, `/inbox <search>` and `/inbox signout`.
`crates/crew-app/src/inbox/signin.rs` handles the sign-in, reusing the loopback listener from
`crates/crew-app/src/oauth.rs`, which now matches Google's `state`. The grant is a 0600
`gmail.json` beside `credentials.json`. The Gmail calls run on a worker thread
(`crates/crew-app/src/inbox/api.rs`), with each page's thread metadata fetched concurrently.
The pane has a list, a reader, search and `o` for Gmail, and its nav row shows the unread
count. Tests run against stub servers of Google's endpoints. Shots on the Ink light page and
glass.

**Not yet:** a live sign-in against Google (needs the user's client), a nav card while the pane
is closed (item 6), a shot on the dark page. Phases 2 and 3 are untouched.
