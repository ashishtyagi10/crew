# Loop — five AI, five UI, five crew, five smith and five inbox rounds

**Status: IN PROGRESS.** Set by the user on 2026-10-30, after the theme loop: *"run ai
enhancement, ui enhancement, crew enhancement, smith enhancement and inbox enhancement loop 5
times each and release after each version"*.

## Rules that hold every round

- **One round, one release.** Each ships through `scripts/release.sh` (it picks the version,
  gates `crew-app` plus the crates in `EXTRA`, merges `--no-ff`, tags and pushes main and the
  tag together). The lanes take turns — AI, UI, crew, smith, inbox — so no lane waits on
  another, and only one release runs at a time.
- **AI** rounds follow `/improve` (`.superpowers/sdd/ai-loop-2026-09-14.md`): one harness
  feature, the smallest honest version, the changelog naming the tool the idea came from, and
  "unit tests only" said plainly where no live probe reaches it.
- **UI** rounds follow a shot survey: layout, spacing, clipping and legibility rather than more
  palette work (the theme loop just ended). Nothing new on screen without a shot.
- **Crew** rounds follow `/crew`: the terminal and the panes — escape sequences, selection,
  scrollback, the multiplexer — never an overlay, never a layout switcher, keys pass through.
- **Smith** rounds follow `/smith-loop` (`.superpowers/sdd/smith-loop-2026-10-16.md`): depth,
  trustworthy feedback, drawn marks that carry information, and a bloat budget.
- **Inbox** rounds follow the inbox loops' rules: a round fixes, simplifies or polishes; nothing
  a test does opens a browser or reads the real grant, Downloads or Reminders.
- Every file stays under the 200-line cap and no file in `line-cap-debt.txt` grows; a test
  fails without each fix; no scratch file stays in the tree while `release.sh` runs (it commits
  with `git add -A`); its log is read for `RELEASED` before the next round starts, and the
  Windows and Coverage runs are read after.

## Log

**Round S1 (v0.29.29): a Claude Code reply counts its whole prompt.**

- **The survey** found the relay's trailer reading "2 in": `claudestream.rs` took the
  `result` line's `input_tokens`, which on Anthropic is the uncached remainder only.
- **Measured** on a live `claude -p` run (a Read, then the answer): the result usage is
  summed over both calls (4 uncached, 19,113 written, 41,326 read) and `iterations` holds the
  last call (2 + 319 + 30,060). The count now takes that last prompt whole, through the API
  path's own `anthropic_input` — 4 → 30,381.

**Round A1 (v0.29.30): Esc stops Claude Code where it stands.**

- **The survey** found the relay's read loop (`claudeagent.rs`, and `run.rs` for codex and
  opencode) watching only its idle deadline. The dial blocks its thread, so the harness's
  race against the stop never reached it, and Claude Code went on editing after Esc.
- **Measured:** TERM (or INT) to a live `claude -p` that was running `sleep 47` through its
  Bash tool ended the sleep and the CLI within three seconds. `clistop.rs` sends TERM, then
  KILL after two seconds. The CLI stays in the broker's process group, because closing a
  pane kills that group.
- **Proof:** fake CLIs that sleep for 30 s end within half a second of the stop, on both
  loops. A dial that ends on the stop ends the turn stopped; with the harness guard removed,
  that test fails. The broker was not driven end to end.
